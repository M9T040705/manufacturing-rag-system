# 技术选型决策记录

> 本文档记录项目中关键技术组件的选型过程、对比分析和最终决策。

## 1. 向量数据库选型

### 候选方案

| 方案 | 类型 | 开源 | 部署方式 |
|------|------|------|----------|
| Milvus | 独立向量数据库 | ✅ Apache 2.0 | 独立服务/分布式 |
| Weaviate | 向量数据库 | ✅ BSD-3 | 独立服务 |
| Qdrant | 向量数据库 | ✅ Apache 2.0 | 独立服务 |
| FAISS | 向量检索库 | ✅ MIT | 嵌入式库 |
| Chroma | 向量数据库 | ✅ Apache 2.0 | 嵌入式/独立服务 |
| Pinecone | 云服务 | ❌ 闭源 | SaaS |

### 对比分析

| 维度 | Milvus | Weaviate | Qdrant | FAISS |
|------|--------|----------|--------|-------|
| 最大规模 | 十亿级 | 亿级 | 亿级 | 千万级(内存) |
| 索引类型 | 10+ 种 | HNSW/IVF | HNSW | HNSW/IVF |
| 动态增删 | ✅ 实时 | ✅ 实时 | ✅ 实时 | ❌ 需重建 |
| 分布式 | ✅ 原生支持 | ✅ | ✅ | ❌ |
| 多租户 | ✅ 集合/分区 | ✅ | ✅ | ❌ |
| 过滤检索 | ✅ 标量过滤 | ✅ | ✅ | 需自行实现 |
| 中文社区 | 活跃 | 一般 | 一般 | 活跃 |
| 运维复杂度 | 中(依赖etcd/minio) | 低 | 低 | 零运维 |
| GPU加速 | ✅ | ❌ | ❌ | ✅ |

### 决策

**选择 Milvus 2.4**

**理由**：
1. 制造业企业文档量预计 10 万+，且持续增长，需要支持大规模向量
2. 需要实时增量更新文档，FAISS 无法满足动态增删需求
3. Milvus 由 Zilliz 维护，中文社区活跃，文档完善
4. 支持标量过滤，可按部门、文档类型、时间范围过滤检索结果
5. 支持 GPU 加速，大规模检索时性能更优
6. 私有化部署，数据不出厂

**权衡**：Milvus 运维复杂度较高（依赖 etcd 和 minio），但通过 Docker Compose 一键部署可降低运维成本。

## 2. 嵌入模型选型

### 候选方案

| 模型 | 维度 | 中文效果 | 开源 | 参数量 |
|------|------|----------|------|--------|
| BGE-large-zh-v1.5 | 1024 | SOTA | ✅ MIT | 326M |
| BGE-base-zh-v1.5 | 768 | 优秀 | ✅ MIT | 109M |
| m3e-large | 1024 | 优秀 | ✅ | 326M |
| text2vec-large-chinese | 1024 | 良好 | ✅ | 326M |
| text-embedding-ada-002 | 1536 | 一般(中文) | ❌ 闭源 | - |
| GTE-large-zh | 1024 | 优秀 | ✅ | 326M |

### 对比分析（C-MTEB 中文检索排行榜）

| 模型 | T2Retrieval | MMarcoRetrieval | 平均 |
|------|-------------|-----------------|------|
| BGE-large-zh-v1.5 | 72.4 | 82.1 | 77.6 |
| GTE-large-zh | 70.8 | 80.3 | 75.8 |
| m3e-large | 69.2 | 78.5 | 74.1 |
| BGE-base-zh-v1.5 | 67.8 | 76.2 | 72.3 |
| text2vec-large | 65.3 | 73.1 | 69.5 |

### 决策

**选择 BGE-large-zh-v1.5**

**理由**：
1. C-MTEB 中文检索排行榜 SOTA，中文语义理解能力最强
2. 1024 维向量，区分度高，检索精度好
3. 支持指令微调（Instruction-tuning），可针对制造业领域进一步优化
4. 开源可私有化部署，数据不出厂
5. 326M 参数，A10 GPU 可轻松承载，嵌入速度快
6. 智源研究院维护，持续迭代更新

**实际效果**：在 500 条制造业评测集上，召回率比 text2vec 高 12%。

## 3. Reranker 模型选型

### 候选方案

| 模型 | 中文效果 | 开源 | 参数量 |
|------|----------|------|--------|
| bge-reranker-v2-m3 | SOTA | ✅ MIT | 568M |
| bge-reranker-large | 优秀 | ✅ MIT | 560M |
| bge-reranker-base | 良好 | ✅ MIT | 109M |
| Cohere Rerank | 优秀 | ❌ 闭源 | - |
| mT5-reranker | 良好 | ✅ | 580M |

### 决策

**选择 bge-reranker-v2-m3**

**理由**：
1. 多语言支持（中/英/多语），跨语言检索场景表现优异
2. 支持长文本（最大 8192 token），适合长文档片段精排
3. 开源可私有化部署
4. 在中文检索精排任务上表现 SOTA

**效果**：引入 Reranker 后，最终答案准确率从 78% 提升到 89%。

## 4. LLM 推理框架选型

### 候选方案

| 框架 | 连续批处理 | PagedAttention | 吞吐量 | 部署复杂度 |
|------|-----------|----------------|--------|-----------|
| vLLM | ✅ | ✅ | 高 | 低 |
| Text Generation Inference (TGI) | ✅ | ❌ | 中 | 中 |
| Ollama | ❌ | ❌ | 低 | 极低 |
| llama.cpp | ❌ | ❌ | 低 | 低 |
| FasterTransformer | ✅ | ❌ | 高 | 高 |

### 对比分析

| 维度 | vLLM | TGI | Ollama |
|------|------|-----|--------|
| 吞吐量(相对) | 3x | 1.8x | 1x |
| 首字延迟 | 低 | 中 | 高 |
| OpenAI兼容API | ✅ | ✅ | ✅ |
| 流式输出 | ✅ | ✅ | ✅ |
| 多GPU张量并行 | ✅ | ✅ | ❌ |
| 量化支持 | ✅(GPTQ/AWQ) | ✅ | ✅ |
| 社区活跃度 | 非常活跃 | 活跃 | 活跃 |
| 生产就绪 | ✅ | ✅ | ❌(开发/测试) |

### 决策

**选择 vLLM 0.6**

**理由**：
1. PagedAttention 技术，KV Cache 显存利用率提升 2-4 倍
2. 连续批处理（Continuous Batching），吞吐量比 TGI 高 1.5-2 倍
3. OpenAI 兼容 API，无缝对接 LangChain
4. 支持多 GPU 张量并行，可扩展模型规模
5. 社区非常活跃，快速迭代，支持最新模型
6. 生产环境广泛验证（Anyscale、Roblox 等公司生产使用）

**实际效果**：Qwen2.5-14B 在 A10 单卡上，vLLM 吞吐量是 HuggingFace Transformers 的 3 倍。

## 5. LLM 模型选型

### 候选方案

| 模型 | 参数量 | 中文能力 | 开源 | 推理显存(FP16) |
|------|--------|----------|------|-----------------|
| Qwen2.5-14B-Instruct | 14B | SOTA | ✅ Apache 2.0 | 28GB |
| Qwen2.5-7B-Instruct | 7B | 优秀 | ✅ Apache 2.0 | 14GB |
| DeepSeek-V2-Lite | 16B | 优秀 | ✅ MIT | 32GB |
| Llama-3.1-8B-Instruct | 8B | 一般 | ✅ | 16GB |
| GLM-4-9B-Chat | 9B | 优秀 | ✅ | 18GB |

### 决策

**选择 Qwen2.5-14B-Instruct（本地）+ DeepSeek（云端兜底）**

**理由**：
1. Qwen2.5-14B 在中文理解、逻辑推理、代码生成上表现 SOTA
2. 14B 参数在 A10（24GB显存）上可部署，推理速度可接受
3. 阿里云维护，持续迭代，工具调用能力强
4. Apache 2.0 协议，可商用
5. 本地部署保障数据安全，云端兜底保障可用性

**云端兜底选择 DeepSeek**：
- 中文理解能力强，价格便宜（约 1元/百万token）
- API 兼容 OpenAI 格式，切换成本低
- 作为本地故障时的兜底，不影响数据安全（兜底时不传输敏感数据）

## 6. OCR 引擎选型

### 候选方案

| 引擎 | 中文准确率 | 开源 | GPU加速 | 部署复杂度 |
|------|-----------|------|---------|-----------|
| PaddleOCR | 高(95%+) | ✅ Apache 2.0 | ✅ | 中 |
| Tesseract | 中(80%+) | ✅ Apache 2.0 | ❌ | 低 |
| EasyOCR | 中高 | ✅ | ✅ | 低 |
| 百度OCR API | 高 | ❌ 闭源 | - | 极低(SaaS) |
| 阿里OCR API | 高 | ❌ 闭源 | - | 极低(SaaS) |

### 决策

**选择 PaddleOCR 2.7**

**理由**：
1. 中文识别准确率 > 95%，远超 Tesseract
2. 支持倾斜文本、手写体、表格识别
3. 开源可私有化部署，数据不出厂
4. 支持 GPU 加速，批量处理速度快
5. 百度飞桨维护，中文场景优化最好

## 7. API 框架选型

### 候选方案

| 框架 | 异步 | 自动文档 | 性能 | 类型安全 | 生态 |
|------|------|----------|------|----------|------|
| FastAPI | ✅ 原生 | ✅ Swagger/ReDoc | 高 | ✅ Pydantic | 活跃 |
| Flask | ❌(需扩展) | ❌(需扩展) | 中 | ❌ | 非常活跃 |
| Django | ❌ | ✅ | 中 | ✅ | 非常活跃 |
| Tornado | ✅ | ❌ | 高 | ❌ | 一般 |

### 决策

**选择 FastAPI 0.115**

**理由**：
1. 原生异步支持，高并发性能优异
2. 自动生成 Swagger API 文档，开发效率高
3. Pydantic 类型校验，请求/响应类型安全
4. 社区活跃，生态完善，中间件丰富
5. 支持 SSE 流式输出，满足 LLM 流式响应需求

## 8. 选型总结

| 模块 | 最终选型 | 核心理由 |
|------|----------|----------|
| 向量库 | Milvus 2.4 | 大规模、动态增删、私有化 |
| 嵌入模型 | BGE-large-zh-v1.5 | 中文SOTA、可微调、开源 |

| LLM模型 | Qwen2.5-14B + DeepSeek | 本地私有化+云端兜底 |
| OCR引擎 | PaddleOCR 2.7 | 中文准确率高、开源、GPU加速 |
| API框架 | FastAPI 0.115 | 异步高性能、自动文档、类型安全 |
| 缓存 | Redis 7 | 高性能、丰富数据结构 |
