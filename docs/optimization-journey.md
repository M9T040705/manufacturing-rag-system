# 效果优化历程

> 本文档记录 RAG 系统从基线 62% 准确率优化到 91% 的完整过程，包括每个优化阶段的思路、方法、数据和经验总结。

## 优化总览

| 阶段 | 准确率 | 提升 | 关键优化 |
|------|--------|------|----------|
| 基线 | 62% | - | 固定分块 + 纯向量检索 |
| V1 | 71% | +9% | 语义分块（标题感知） |
| V2 | 78% | +7% | 混合检索（向量+BM25） |
| V3 | 89% | +11% | Reranker 精排 |
| V4 | 91% | +2% | 行业词典 + Prompt 优化 |

**评测集**：500 条真实业务问答，涵盖设备操作、工艺规范、故障排查、质量标准等场景
**评测指标**：答案准确率（人工标注参考答案，LLM-as-Judge 辅助评分）

---

## 阶段一：基线系统（62%）

### 配置

- 分块：固定长度 512 token，overlap 50
- 检索：纯向量检索（BGE-base），Top-K=5
- LLM：Qwen-7B，temperature=0.7
- Prompt：通用问答模板

### 问题分析

通过对 500 条评测集的错误案例分析，发现主要问题：

| 问题类型 | 占比 | 典型案例 |
|----------|------|----------|
| 检索未命中 | 38% | "调质处理的工艺参数" → 检索到"热处理概述"而非具体参数 |
| 分块切断上下文 | 25% | 工艺步骤被切分到两个块，只检索到一半 |
| 专业术语匹配差 | 18% | "HRC硬度"被分词为"H/R/C/硬度"，向量匹配失效 |
| LLM 幻觉 | 12% | 资料中没有的参数，模型自行编造 |
| 其他 | 7% | - |

### 关键发现

1. **固定分块是最大瓶颈**：制造业文档有清晰的标题层级，固定分块会切断工艺步骤和参数表格
2. **纯向量检索不适合专业术语**：设备型号、工艺参数等精确匹配场景，向量检索召回率低
3. **通用 Prompt 不够约束**：模型容易在资料不足时编造答案

---

## 阶段二：语义分块优化（71%，+9%）

### 优化思路

制造业技术文档通常有清晰的结构：章节标题 → 小节标题 → 正文 → 表格。固定长度分块会破坏这种结构，导致检索到的片段上下文不完整。

**解决方案**：按标题层级语义分块

### 实现方法

1. **标题识别**：用正则匹配中文标题格式（一、二、1. 1.1 第一章等）
2. **层级切分**：先按一级标题切分，再按二级标题切分，以此类推
3. **长度兜底**：如果某个标题下内容超过 512 token，再按固定长度切分
4. **Overlap 保留**：相邻块之间保留 64 token 重叠
5. **标题注入**：每个块开头注入所属标题路径，增强上下文

```python
# 分块策略对比
# 固定分块：[token 0-511] [token 462-973] ...
# 语义分块：
#   [标题1.1 + 内容...]
#   [标题1.2 + 内容...]
#   [标题1.3 + 内容(超长部分1)...]
#   [标题1.3 + 内容(超长部分2)...]
```

### 术语保护机制

在分块时检查切点是否在专业术语中间，如果是则移动切点到术语结束位置。

```python
MANUFACTURING_TERMS = {"调质处理", "淬火", "回火", "金相组织", "HRC", "HB", ...}

def _avoid_term_split(text, pos):
    for term in MANUFACTURING_TERMS:
        term_pos = text.find(term, pos-10, pos+10)
        if term_pos != -1 and term_pos < pos < term_pos + len(term):
            return term_pos + len(term)
    return pos
```

### 效果数据

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 答案准确率 | 62% | 71% | +9% |
| 检索召回率 | 68% | 81% | +13% |
| 上下文完整度 | 55% | 82% | +27% |

### 错误案例减少

- "分块切断上下文"类错误从 25% 降到 8%
- "检索未命中"类错误从 38% 降到 29%

### 经验总结

1. **语义分块对结构化文档效果显著**：标题层级是最天然的语义边界
2. **标题注入很重要**：将标题路径注入每个块开头，能显著提升检索相关性
3. **术语保护避免关键信息切断**：专业术语被切断会导致检索完全失效
4. **分块大小需要权衡**：太小上下文不足，太大引入噪声，512 token 是较好的平衡点

## 阶段三：混合检索（78%，+7%）

### 优化思路

语义分块解决了上下文完整度问题，但"专业术语匹配差"的问题仍然存在。

向量检索的本质是语义相似度，但在制造业场景中：
- 设备型号（"CNC-850"）、零件编号（"GB/T 699-2015"）需要精确匹配
- 工艺参数（"HRC 58-62"）需要关键词匹配
- 向量检索对这些精确匹配场景表现不佳

**解决方案**：向量检索 + BM25 关键词检索，双路召回 + RRF 融合

### 实现方法

1. **BM25 索引**：对所有文档块构建 BM25 索引（rank-bm25 库）
2. **中文分词**：字符级 + 2-gram 混合分词，适配中文无空格特点
3. **双路召回**：向量检索返回 Top-20，BM25 检索返回 Top-20
4. **RRF 融合**：Reciprocal Rank Fusion 算法融合两路排序
   ```
   RRF_score = sum(1 / (k + rank_i))  # k=60
   ```
5. **加权调整**：向量权重 0.7，BM25 权重 0.3（制造业语义更重要）

### 效果数据

| 指标 | 优化前(纯向量) | 优化后(混合) | 提升 |
|------|---------------|-------------|------|
| 答案准确率 | 71% | 78% | +7% |
| 专业术语查询准确率 | 62% | 85% | +23% |
| 设备型号查询召回率 | 55% | 88% | +33% |
| 整体检索召回率 | 81% | 88% | +7% |

### 典型案例

| 查询 | 纯向量检索结果 | 混合检索结果 |
|------|---------------|-------------|
| "CNC-850 加工中心参数" | 检索到"数控机床概述"（语义相关但不是目标设备） | 精确匹配到"CNC-850 操作手册" |
| "HRC 58-62 是什么热处理" | 检索到"硬度检测方法" | 匹配到"淬火工艺规范 HRC 58-62" |
| "GB/T 699-2015 是什么标准" | 检索到"钢材分类" | 精确匹配到"GB/T 699-2015 优质碳素结构钢" |

### 经验总结

1. **混合检索是专业领域 RAG 的必选项**：纯向量检索无法满足精确匹配需求
2. **BM25 对中文需要特殊处理**：字符级 + 2-gram 分词比结巴分词效果更稳定
3. **RRF 比加权分数融合更鲁棒**：避免了向量分数和 BM25 分数量纲不一致的问题
4. **权重需要根据领域调整**：制造业语义更重要，向量权重 0.7；法律领域关键词更重要，可能需要 BM25 权重更高

## 阶段四：Reranker 精排（89%，+11%）

### 优化思路

混合检索解决了召回率问题，但返回的 Top-10 结果中，最相关的不一定排在最前面。

向量检索和 BM25 都是 Bi-encoder 架构（查询和文档分别编码），计算速度快但精度有限。Reranker 使用 Cross-encoder 架构（查询和文档拼接后一起编码），能更精确地判断相关性。

**解决方案**：两阶段检索 — 召回阶段快速返回 Top-20，精排阶段用 Reranker 选出 Top-5

### 实现方法

1. **模型选择**：bge-reranker-v2-m3（多语言、长文本、中文效果好）
2. **精排流程**：
   ```
   用户查询 → 混合检索 → Top-20 候选
                    ↓
            Reranker 精排（交叉编码）
                    ↓
               Top-5 最终结果
                    ↓
              上下文构建 → LLM 生成
   ```
3. **分数归一化**：Reranker 输出的 logits 通过 sigmoid 归一化到 0-1
4. **阈值过滤**：精排分数低于 0.3 的结果被过滤，减少无关上下文干扰

### 性能权衡

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 向量检索 | ~30ms | Milvus HNSW 索引 |
| BM25 检索 | ~20ms | 内存计算 |
| Reranker 精排 | ~150ms | GPU 推理，Top-20 |
| **总计** | **~200ms** | 可接受 |

Reranker 增加了约 150ms 延迟，但准确率提升了 11%，投入产出比很高。

### 效果数据

| 指标 | 优化前(无Rerank) | 优化后(有Rerank) | 提升 |
|------|------------------|------------------|------|
| 答案准确率 | 78% | 89% | +11% |
| Top-1 命中率 | 62% | 85% | +23% |
| 答案相关性 | 75% | 92% | +17% |
| 引用准确率 | 68% | 88% | +20% |

### 错误案例分析

引入 Reranker 后，剩余的错误主要集中在：
- **多文档综合问答**：需要跨多个文档综合信息的问题（占 35%）
- **推理计算类问题**：需要基于资料进行计算或推理的问题（占 28%）
- **资料缺失**：知识库中确实没有相关内容（占 22%）
- **其他**（占 15%）

### 经验总结

1. **Reranker 是准确率提升的最大单点优化**：从 78% 到 89%，提升 11 个百分点
2. **两阶段检索是标准架构**：召回保证覆盖率，精排保证准确率
3. **精排 Top-K 数量需要权衡**：Top-20 精排是速度和效果的平衡点
4. **Reranker 分数可以作为答案置信度**：分数低的问题可以触发"资料不足"的兜底回答

## 阶段五：行业词典 + Prompt 优化（91%，+2%）

### 优化思路

经过前四个阶段的优化，系统准确率达到 89%。剩余的错误主要集中在专业术语理解和 LLM 回答规范性上。

**解决方案**：
1. 构建制造业专业术语词典，优化分词和检索
2. 针对制造业场景优化 Prompt，强化"基于资料回答"的约束
3. 增加查询改写，优化用户查询的表达

### 行业词典

构建了 2000+ 条制造业专业术语词典，涵盖：
- 热处理工艺：调质处理、淬火、回火、退火、正火、渗碳、氮化...
- 力学性能：抗拉强度、屈服强度、伸长率、冲击韧性、疲劳强度...
- 加工工艺：车削、铣削、钻削、磨削、CNC、加工中心、电火花...
- 材料标准：GB/T 699、GB/T 700、45#钢、40Cr、Q235...
- 设备维护：预防性维护、预测性维护、故障诊断、点检...

**应用方式**：
- 分块时保护术语不被切断
- BM25 分词时优先匹配术语
- 查询改写时扩展同义词（如"热处理"→"淬火/回火/退火"）

### Prompt 优化

**优化前**：
```
请根据以下资料回答问题。
资料：{context}
问题：{question}
```

**优化后**：
```
你是一个专业的制造业技术知识库助手。

回答规则：
1. 必须严格基于参考资料回答，不得编造资料中没有的信息
2. 如果资料不足，明确说明"根据现有资料无法完整回答"
3. 涉及工艺参数、设备型号、安全规范时，必须标注来源文档
4. 操作类问题给出清晰的步骤说明
5. 回答末尾列出引用来源

参考资料：
{context}

用户问题：{question}
```

**关键改进**：
- 明确角色定位（制造业技术助手）
- 强制"基于资料回答"，禁止编造
- 增加"资料不足"的兜底策略
- 要求标注来源，增强可追溯性
- 针对操作类问题给出步骤说明

### 查询改写

对用户查询进行改写，优化检索效果：
- 同义词扩展："硬度多少"→"硬度/HRC/HB/抗拉强度"
- 术语标准化："cnc"→"CNC/数控加工中心"
- 意图识别：区分"是什么/为什么/怎么做/参数是多少"

### 效果数据

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 答案准确率 | 89% | 91% | +2% |
| 专业术语查询准确率 | 85% | 93% | +8% |
| 幻觉率（编造答案） | 8% | 2% | -6% |
| 答案可追溯率 | 82% | 95% | +13% |

### 经验总结

1. **行业词典是专业领域 RAG 的基础设施**：虽然只提升 2% 整体准确率，但专业术语查询提升了 8%
2. **Prompt 优化的投入产出比很高**：不需要改代码，只需要优化提示词，就能显著减少幻觉
3. **"资料不足"的兜底策略很重要**：明确告诉模型"不知道就说不知道"，比强行回答效果好得多
4. **查询改写是被低估的优化点**：用户查询表达不规范是检索失败的常见原因

## 优化方法论总结

### RAG 系统优化的一般顺序

根据本项目的经验，RAG 系统优化建议按以下顺序进行：

```
1. 语义分块（基础，+9%）
   ↓
2. 混合检索（召回，+7%）
   ↓
3. Reranker 精排（准确率，+11%）
   ↓
4. Prompt 优化（规范性，+2%）
   ↓
5. 行业词典/查询改写（领域适配，+2%）
```

### 各优化阶段的投入产出比

| 优化项 | 准确率提升 | 实现难度 | 投入产出比 |
|--------|-----------|----------|-----------|
| Reranker 精排 | +11% | 中 | ⭐⭐⭐⭐⭐ |
| 语义分块 | +9% | 低 | ⭐⭐⭐⭐⭐ |
| 混合检索 | +7% | 中 | ⭐⭐⭐⭐ |
| Prompt 优化 | +2% | 极低 | ⭐⭐⭐⭐⭐ |
| 行业词典 | +2% | 高（需人工构建） | ⭐⭐⭐ |

### 评测驱动的优化流程

1. **建立评测集**：500 条真实业务问答，人工标注参考答案
2. **每次优化后跑评测**：用数据说话，不凭感觉
3. **错误案例分析**：每次优化后分析剩余错误，找到下一个优化方向
4. **A/B 测试**：对比不同配置的效果，选择最优方案
5. **持续迭代**：RAG 优化没有终点，持续收集 bad case 持续优化

### 常见误区

1. **盲目换大模型**：模型从 7B 换到 14B，准确率可能只提升 2-3%，但成本翻倍。检索质量才是瓶颈。
2. **只调参不改架构**：调整 Top-K、chunk_size 只能带来微小提升，架构优化（混合检索、Reranker）提升更大。
3. **忽视评测**：没有评测集就无法量化优化效果，容易陷入"感觉变好了"的错觉。
4. **过度优化检索**：检索准确率到 90% 以后，边际效益递减，此时应该关注 LLM 生成质量。
