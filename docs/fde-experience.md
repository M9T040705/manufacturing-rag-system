# FDE 落地经验总结

> 本文档从 FDE（Forward Deployed Engineer，前沿部署工程师）视角，总结制造业 RAG 系统从需求调研到交付运维的完整落地经验。

## 1. 什么是 FDE 视角

FDE 的核心职责不是"写代码"，而是**把 AI 能力落地到客户真实生产环境，并对最终业务结果负责**。

与传统研发的区别：

| 维度 | 传统研发 | FDE |
|------|----------|-----|
| 工作地点 | 办公室 | 客户现场 |
| 需求来源 | 产品经理的 PRD | 客户一线的模糊需求 |
| 交付标准 | 功能完成 | 业务指标提升 |
| 核心能力 | 编码 | 需求拆解 + 系统集成 + 客户沟通 |
| 成功标准 | 代码上线 | 客户真的用起来了 |

## 2. 项目落地全流程

### 2.1 第一阶段：需求调研（驻场 2 周）

#### 目标
- 理解客户业务场景和痛点
- 明确项目边界和成功指标
- 梳理现有系统和数据资产

#### 关键动作

**1.  stakeholder 访谈**

访谈对象覆盖决策层、管理层、执行层：
- 技术总监：关注系统架构、数据安全、运维成本
- 车间主任：关注工人能不能用起来、回答准不准
- 一线技术员：关注查资料快不快、回答专不专业
- IT 部门：关注私有化部署、系统对接、权限管理

**关键发现**：
- 技术员查资料平均 40 分钟/次，80% 的时间花在"找文档"而非"读文档"
- 文档分散在 3 个系统：OA 系统、共享文件夹、老旧文档管理系统
- 12 万份文档中，约 30% 是扫描件，无法全文检索
- 新人上手周期 2 个月，主要瓶颈是"不知道去哪查"

**2. 数据资产盘点**

| 系统 | 文档数量 | 格式 | 接入难度 |
|------|----------|------|----------|
| OA 系统 | 5 万 | PDF/Word | 中（有 REST API） |
| 共享文件夹 | 4 万 | PDF/Word/PPT | 低（SMB 协议） |
| 老旧文档系统 | 3 万 | 扫描件 PDF | 高（无 API，需数据库直连） |

**3. 成功指标对齐**

与客户共同定义可量化的成功指标：
- 资料查找时间下降 ≥ 50%
- 答案准确率 ≥ 85%
- 系统可用性 ≥ 99.5%
- 新人上手周期缩短 ≥ 30%

#### 经验总结

1. **一定要去一线**：在办公室听汇报和在车间看技术员实际操作，得到的需求完全不同
2. **成功指标要量化**："提升效率"是废话，"查找时间从40分钟降到20分钟"才是可验证的指标
3. **数据盘点要做实**：客户说"我们有 10 万份文档"，实际可能只有 6 万份可用，其余是重复或损坏的
4. **识别决策者和使用者**：买单的人和用的人往往不是同一批人，需求要同时满足双方

### 2.2 第二阶段：方案设计（1 周）

#### 目标
- 设计满足客户需求的技术方案
- 明确系统边界和集成方式
- 输出可评审的技术方案文档

#### 关键设计决策

**1. 私有化部署方案**

客户要求"数据不出厂"，因此必须私有化部署。

| 组件 | 部署方式 | 说明 |
|------|----------|------|
| LLM 推理 | 本地 GPU 服务器 | A10 单卡，Qwen2.5-14B |
| 向量库 | 内网 Milvus 集群 | 3 节点，数据持久化 |
| 应用服务 | Docker 容器 | K8s 编排，可水平扩展 |
| 模型权重 | 本地文件系统 | 离线下载，不访问公网 |

**2. 老旧系统对接方案**

最棘手的是老旧文档系统（无 API，SQL Server 2008）。

**方案对比**：
- 方案 A：数据库直连读取（风险：影响生产系统性能）
- 方案 B：每日凌晨批量导出（风险：数据延迟 1 天）
- 方案 C：中间件同步（成本：需额外开发）

**最终选择**：方案 B（每日凌晨增量同步），原因：
- 客户文档更新频率低（日均新增 200 份），1 天延迟可接受
- 不影响生产系统，风险最低
- 实现简单，运维成本低

**3. 安全合规方案**

- SSO 统一认证：对接客户 OA 的 JWT 认证
- 权限隔离：基于部门的文档访问控制
- 审计日志：所有查询和操作记录写入 OA 审计系统
- 数据加密：传输 HTTPS，存储 AES-256

#### 经验总结

1. **方案要给客户选择权**：不要只给一个方案，给 2-3 个方案并说明 trade-off，让客户参与决策
2. **老旧系统对接是 FDE 的核心价值**：客户最头疼的不是 AI 模型，而是"怎么把老系统的数据弄出来"
3. **安全合规要提前考虑**：不要等方案做完了才想安全，很多客户有等保三级要求，架构要从一开始就满足
4. **方案文档要写得让客户能看懂**：不要全是技术术语，要用业务语言解释技术选择

### 2.3 第三阶段：开发部署（4 周）

#### 目标
- 完成系统开发和测试
- 在客户环境完成部署
- 导入历史文档数据

#### 关键挑战与解决方案

**挑战 1：内网环境无法 pip install**

客户内网完全隔离，无法访问 PyPI。

**解决方案**：
- 在外网环境下载所有依赖包（`pip download -r requirements.txt -d ./packages`）
- 打包成离线安装包，通过 U 盘拷贝到内网
- 在内网执行 `pip install --no-index --find-links=./packages -r requirements.txt`

**挑战 2：扫描件 OCR 准确率低**

30% 的文档是扫描件，普通 OCR 对表格和公式识别准确率只有 60%。

**解决方案**：
- PaddleOCR + 表格识别模型（PP-Structure）
- 针对制造业文档微调 OCR 模型（用 500 份标注文档）
- OCR 后处理：专业术语纠错、表格结构还原
- 最终 OCR 准确率从 60% 提升到 92%

**挑战 3：GPU 驱动兼容问题**

客户服务器是 CentOS 7.9，NVIDIA 驱动版本 470，不支持最新 CUDA 12。

**解决方案**：
- 降级使用 CUDA 11.8 兼容的 PyTorch 和 vLLM 版本
- Docker 容器内固定 CUDA 版本，避免宿主机依赖
- 编写详细的驱动升级指南，协助客户 IT 部门升级

**挑战 4：12 万份文档入库耗时长**

12 万份文档，OCR + 分块 + 嵌入，单 GPU 需要 7 天。

**解决方案**：
- 批量并行处理：OCR 用 CPU 多进程，嵌入用 GPU 批量
- 优先级排序：先入库高频使用的文档（设备手册、工艺规范），再入库低频文档
- 增量入库：上线时先入库 5 万份核心文档，后续后台持续入库
- 最终核心文档 2 天完成入库，全量 5 天完成

#### 经验总结

1. **内网部署是 FDE 的日常**：要习惯没有公网、没有 pip、没有 Docker Hub 的环境，提前准备离线包
2. **OCR 是制造业 RAG 的隐藏大坑**：扫描件比例往往超出预期，OCR 质量直接决定系统上限
3. **GPU 环境问题要提前排查**：不要等部署当天才发现驱动不兼容，提前要到服务器信息做兼容性验证
4. **数据导入要分批**：不要等所有数据都导完才上线，先上核心数据让客户用起来，再持续补全

### 2.4 第四阶段：效果调优（2 周）

#### 目标
- 将答案准确率从基线 62% 优化到 85% 以上
- 建立评测体系和持续优化机制

#### 调优过程

详细优化过程请参考 [效果优化历程](optimization-journey.md)。

**关键动作**：
1. 构建 500 条真实业务问答评测集（与客户技术员共同标注）
2. 分阶段优化：语义分块 → 混合检索 → Reranker → Prompt 优化
3. 每周与客户 review 优化效果，用数据说话
4. 建立 bad case 收集机制，持续迭代

**最终效果**：
- 答案准确率：62% → 91%
- 资料查找时间：40 分钟 → 10 分钟（下降 75%）
- 新人上手周期：2 个月 → 3 周（缩短 62%）

#### 经验总结

1. **评测集要和客户一起建**：客户标注的评测集才是"客户认为的正确答案"，自己建的评测集可能偏离客户需求
2. **优化要用数据驱动**：每次优化后跑评测，用准确率数字说话，不要说"我觉得变好了"
3. **bad case 是最好的优化方向**：让客户用起来，收集他们觉得"回答不好"的问题，针对性优化
4. **调优阶段要驻场**：和客户技术员一起用系统，现场发现问题，现场调整，效率最高

### 2.5 第五阶段：交付培训（1 周）

#### 目标
- 完成系统交付和知识转移
- 培训客户运维人员和终端用户
- 建立长期支持机制

#### 交付物清单

| 交付物 | 说明 | 接收方 |
|--------|------|--------|
| 系统源代码 | Git 仓库 | 客户 IT 部门 |
| 部署运维手册 | 部署、配置、监控、备份、故障排查 | 客户运维人员 |
| API 接口文档 | Swagger 文档 + 接口说明 | 客户开发人员 |
| 用户使用手册 | 系统功能介绍、操作指南、常见问题 | 终端用户 |
| 培训材料 | PPT + 操作视频 | 培训使用 |
| 评测报告 | 准确率、延迟、业务指标提升数据 | 客户管理层 |
| 运维培训 | 2 天实操培训 | 客户运维人员 |
| 用户培训 | 3 场分部门培训 | 终端用户 |

#### 培训设计

**运维人员培训（2 天）**：
- Day 1：系统架构、部署操作、配置管理、日志查看
- Day 2：监控告警、备份恢复、故障排查、性能调优、实操演练

**终端用户培训（1 小时/场）**：
- 系统能做什么、不能做什么
- 如何提问能得到更好的回答（Prompt 技巧）
- 如何查看引用来源、验证答案准确性
- 遇到问题如何反馈

#### 经验总结

1. **交付不是扔给客户就完事**：要确保客户能自己运维、自己用起来，否则项目就是失败的
2. **培训要分角色**：运维人员关心怎么修，终端用户关心怎么用，不要混在一起培训
3. **文档要写得让客户能看懂**：不要用太多内部术语，假设读者是刚接触这个系统的人
4. **留下长期支持通道**：建立微信群/工单系统，客户遇到问题能找到人，这是客户满意度的关键

## 3. FDE 核心能力模型

### 3.1 技术能力

| 能力 | 说明 | 本项目体现 |
|------|------|-----------|
| 全栈开发 | 前后端、API、数据库 | FastAPI + Milvus + Redis |
| 系统集成 | 对接老旧系统、第三方 API | OA 系统对接、数据库直连 |
| 私有化部署 | 离线环境、GPU 配置、Docker | 内网部署、驱动兼容 |
| 性能调优 | 检索优化、推理加速、缓存 | 准确率 62%→91% |
| 故障排查 | 日志分析、问题定位、快速修复 | OCR 失败、GPU OOM 等 |

| 项目管理 | 进度管理、风险管理、干系人管理 | 10 周交付，5 个阶段 |
| 数据思维 | 用数据定义成功、用数据验证效果 | 评测集、准确率、业务指标 |

## 4. 常见坑与避坑指南

### 坑 1：客户说"我们数据很全"

**现实**：客户说有 10 万份文档，实际可用的可能只有 5 万份，其余是重复、损坏、加密的。

**避坑**：
- 驻场第一周就做数据盘点，抽样检查数据质量
- 不要把客户的口头承诺写进合同，要写"以实际可接入数据为准"
- 预留数据清洗的时间和预算

### 坑 2：客户说"这个功能很简单"

**现实**：客户说"就是接一下 OA 系统"，实际 OA 系统是 10 年前的老旧系统，没有 API，数据库表结构混乱。

**避坑**：
- 任何"简单"的系统对接，都要先做技术验证（POC）
- 把对接的复杂度和风险提前告诉客户
- 预留 2-3 倍的对接时间

### 坑 3：模型效果在测试集上很好，上线就崩

**现实**：用通用评测集准确率 90%，客户真实问题准确率只有 60%。

**避坑**：
- 一定要用客户的真实数据建评测集
- 上线前做 beta 测试，让客户真实用户试用
- 上线后持续收集 bad case，持续优化

### 坑 4：客户 IT 部门不配合

**现实**：客户 IT 部门担心系统出问题担责任，不配合开权限、开网络。

**避坑**：
- 提前识别 IT 部门的关键决策人，建立关系
- 把系统设计成对现有系统影响最小的方案（只读、异步、不直连生产库）
- 提供详细的安全评估报告，消除 IT 部门顾虑
- 让业务部门出面推动，比技术人员推动有效 10 倍

### 坑 5：项目交付后没人用

**现实**：系统上线了，功能也正常，但客户员工还是习惯老方式，系统使用率很低。

**避坑**：
- 上线前就要培养种子用户，让他们参与测试和反馈
- 培训要讲"这个系统能帮你省多少时间"，而不是"这个系统有什么功能"
- 找客户内部的"推动者"，让他们在部门内推广
- 定期分享使用数据和成功案例，制造正向反馈

## 5. 总结

FDE 的本质是**"在客户现场解决真实问题的技术特种兵"**。

这个项目的成功，不是因为用了多先进的 AI 模型，而是因为：
1. **深入一线理解真实痛点**：技术员查资料 40 分钟/次，这是真痛点
2. **把老旧系统的数据弄出来**：12 万份文档入库，这是真功夫
3. **用数据证明效果**：查找时间降 75%，准确率 91%，这是真价值
4. **让客户真的用起来**：培训、支持、持续优化，这是真交付

**技术只是工具，解决问题才是目的。** 这就是 FDE 的核心价值。
