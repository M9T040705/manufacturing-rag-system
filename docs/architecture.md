# 架构设计详解

> 本文档详细阐述制造业 RAG 问答系统的架构设计、分层职责、关键技术决策与设计权衡。

## 1. 设计目标

### 1.1 业务目标

- **知识可检索**：将分散在 PDF/Word/PPT/扫描件中的技术文档转化为可智能检索的知识库
- **答案可追溯**：每个回答都标注来源文档和页码，确保答案可信、可验证
- **部署私有化**：纯内网部署，数据不出厂，满足制造业数据安全合规要求
- **效果可量化**：建立评测体系，持续优化检索准确率和回答质量

### 1.2 非功能需求

| 维度 | 要求 | 实现方式 |
|------|------|----------|
| 性能 | P95 问答延迟 < 3s | vLLM 推理优化 + 混合检索 + 缓存 |
| 并发 | 支持 50 并发查询 | FastAPI 异步 + Milvus 并发检索 |
| 可用性 | 99.7% | 本地+云端双模型兜底 + 健康检查 |
| 可扩展性 | 支持百万级文档 | Milvus 分布式向量库 + 水平扩展 |
| 可维护性 | 模块化、可测试 | 分层架构 + 依赖注入 + 单元测试 |

## 2. 分层架构

### 2.1 架构总览

系统采用经典的六层架构，每一层职责单一、接口明确：

```
┌─────────────────────────────────────────────────┐
│  API 层 (FastAPI)                                │
│  路由 / 请求校验 / 响应封装 / 流式输出            │
├─────────────────────────────────────────────────┤
│  业务编排层 (LangChain LCEL)                     │
│  查询改写 / 检索编排 / 上下文构建 / LLM调用      │
├──────────────────┬──────────────────┬───────────┤
│  文档处理层       │  检索层           │  LLM 层   │
│  加载 / 解析      │  向量检索         │  本地推理  │
│  分块 / OCR      │  BM25检索         │  云端兜底  │
│  元数据提取       │  RRF融合          │  流式输出  │
│                  │  Rerank精排       │           │
├──────────────────┴──────────────────┴───────────┤
│  存储层 (Milvus + Redis + 文件系统)               │
│  向量存储 / 缓存 / 原始文档                        │
├─────────────────────────────────────────────────┤
│  系统集成层 (OA 对接)                              │
│  SSO认证 / 增量同步 / 审计日志                     │
└─────────────────────────────────────────────────┘
```

### 2.2 各层职责

#### API 层

**职责**：接收 HTTP 请求，参数校验，调用业务层，封装响应

**关键设计**：
- 使用 FastAPI 异步框架，天然支持高并发
- Pydantic 模型做请求/响应校验，类型安全
- SSE（Server-Sent Events）实现流式输出
- 统一异常处理和错误码
- Prometheus 指标埋点

**核心文件**：`src/api/main.py`, `src/api/schemas.py`

#### 业务编排层

**职责**：编排 RAG 全流程，管理查询改写、检索、精排、生成的执行顺序

**关键设计**：
- 使用 LangChain LCEL（LangChain Expression Language）声明式编排
- 支持查询改写（多轮对话上下文理解）
- 检索结果缓存（Redis），相同查询直接返回
- 引用来源标注，答案可追溯

**处理流程**：
```
用户问题 → 查询改写(可选) → 混合检索 → Rerank精排 → 上下文构建 → LLM生成 → 引用标注 → 返回
```

#### 文档处理层

**职责**：将各种格式的文档转化为标准化的文本块（Chunk）

**关键设计**：
- **多格式加载**：PDF（PyMuPDF）、Word（python-docx）、PPT（python-pptx）、图片（OCR）
- **扫描件检测**：PDF 文本提取量 < 50 字符时自动触发 OCR
- **语义分块**：先按标题层级切分，再按固定长度兜底，overlap 保留上下文
- **术语保护**：制造业专业术语不被切断（2000+ 术语词典）
- **元数据丰富**：来源文件、页码、标题、部门、标签等

**分块策略对比**：

| 策略 | 召回率 | 准确率 | 适用场景 |
|------|--------|--------|----------|
| 固定长度（512token） | 68% | 62% | 通用场景 |
| 固定长度+overlap | 72% | 65% | 通用场景 |
| 标题层级语义分块 | 81% | 71% | 结构化文档 |
| 语义分块+术语保护 | 85% | 76% | 专业领域文档 |

#### 检索层

**职责**：根据用户查询，从向量库中检索最相关的文档片段

**关键设计**：
- **双路召回**：向量语义检索 + BM25 关键词检索
- **RRF 融合**：Reciprocal Rank Fusion 算法融合两路结果，避免单一检索的偏差
- **Rerank 精排**：BGE-Reranker 对 Top-K 结果做交叉编码精排
- **相似度阈值**：过滤低相关结果，减少无关上下文干扰
- **元数据过滤**：支持按部门、文档类型、时间范围过滤

**混合检索架构**：
```
                    ┌─────────────┐
                    │  用户查询    │
                    └──────┬──────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
       ┌─────────────┐          ┌─────────────┐
       │  向量检索    │          │  BM25检索    │
       │ (BGE-large) │          │ (关键词匹配) │
       └──────┬──────┘          └──────┬──────┘
              │                         │
              └────────────┬────────────┘
                           ▼
                   ┌─────────────┐
                   │  RRF 融合    │
                   │ (加权排序)   │
                   └──────┬──────┘
                          ▼
                   ┌─────────────┐
                   │ Rerank精排  │
                   │ (bge-rerank)│
                   └──────┬──────┘
                          ▼
                   ┌─────────────┐
                   │  Top-N 返回  │
                   └─────────────┘
```

#### LLM 推理层

**职责**：根据检索到的上下文，生成准确、专业的回答

**关键设计**：
- **本地优先**：vLLM 部署 Qwen2.5-14B，数据不出内网
- **云端兜底**：本地故障/超时时自动切换 DeepSeek，保障可用性
- **流式输出**：SSE 流式响应，首字延迟 < 500ms
- **Prompt 工程**：制造业场景优化的系统提示词，强制基于参考资料回答
- **温度控制**：temperature=0.3，保证回答的稳定性和准确性

**双模型兜底机制**：
```
请求 → 本地vLLM → 成功? → 是 → 返回结果
                 → 否 → 云端DeepSeek → 成功? → 是 → 返回结果
                                                  → 否 → 返回错误
```

#### 存储层

**职责**：持久化存储向量、缓存、原始文档

**组件选型**：
- **Milvus 2.4**：向量数据库，HNSW 索引，支持十亿级向量
- **Redis 7**：缓存层，缓存查询结果、会话状态、嵌入向量
- **本地文件系统**：存储原始文档和处理后的中间数据

#### 系统集成层

**职责**：对接企业现有 OA 系统，实现身份认证、数据同步、审计日志

**关键设计**：
- **SSO 统一认证**：对接企业 OA 的 JWT/OAuth 认证
- **增量同步**：每日凌晨自动同步 OA 新增/更新文档，支持断点续传
- **审计日志**：所有查询和操作记录写入 OA 审计系统
- **多模式适配**：支持 REST API、数据库直连、文件共享等多种对接方式

## 3. 关键技术决策

### 3.1 为什么选择 Milvus 而非 FAISS？

| 维度 | Milvus | FAISS |
|------|--------|-------|
| 部署方式 | 独立服务，支持分布式 | 嵌入式库，单机 |
| 数据规模 | 十亿级向量 | 千万级（内存限制） |
| 索引类型 | HNSW/IVF/ANNOY 等 10+ 种 | HNSW/IVF 等 |
| 动态增删 | 支持实时增删改 | 需重建索引 |
| 多租户 | 支持集合/分区隔离 | 需自行实现 |
| 运维成本 | 需运维独立服务 | 零运维 |

**决策**：制造业企业文档量预计 10 万+，且需要持续增量更新，选择 Milvus。

### 3.2 为什么选择混合检索而非纯向量检索？

纯向量检索在专业术语查询上存在明显缺陷：
- "调质处理"这类专业术语，向量相似度可能匹配到语义相近但不相关的内容
- 设备型号、零件编号等精确匹配场景，向量检索召回率低

BM25 关键词检索在精确匹配上表现优异，但无法理解语义。

**混合检索 + RRF 融合**结合了两者的优势：
- 向量检索负责语义理解
- BM25 负责关键词精确匹配
- RRF 算法融合排序，避免单一检索的偏差

**效果**：专业术语查询准确率从 68% 提升到 85%。

### 3.3 为什么需要 Reranker？

向量检索的相似度是基于查询和文档的独立编码（Bi-encoder），计算速度快但精度有限。

Reranker 使用交叉编码（Cross-encoder），将查询和文档拼接后一起编码，能更精确地判断相关性。

**两阶段检索策略**：
1. **召回阶段**：向量检索快速返回 Top-50 候选（毫秒级）
2. **精排阶段**：Reranker 对 Top-50 精排，返回 Top-5（百毫秒级）

**效果**：最终答案准确率从 78% 提升到 89%。

## 4. 数据流设计

### 4.1 文档入库流程

```
上传文档 → 格式检测 → 文本提取(PDF/Word/PPT)
                ↓ 文本过少?
                是 → OCR识别 → 文本提取
                ↓
         语义分块(标题感知+术语保护)
                ↓
         元数据提取(来源/页码/标题)
                ↓
         嵌入向量生成(BGE-large)
                ↓
         Milvus批量插入
                ↓
         入库完成(返回块数/向量数)
```

### 4.2 问答流程

```
用户问题 → 查询改写(多轮上下文)
      ↓
  嵌入向量生成
      ↓
  混合检索(向量+BM25)
      ↓
  RRF融合 → Rerank精排 → Top-N
      ↓
  上下文构建(文档拼接+来源标注)
      ↓
  LLM生成(本地vLLM/云端兜底)
      ↓
  引用来源提取 → 响应封装 → 返回
```

## 5. 扩展性设计

### 5.1 水平扩展

- **API 层**：无状态设计，可通过 Docker Swarm/K8s 水平扩展
- **检索层**：Milvus 支持分片和副本，可水平扩展
- **LLM 层**：vLLM 支持多 GPU 张量并行，可扩展模型规模

### 5.2 插件化扩展

- **新文档格式**：在 `DocumentLoader` 中新增格式处理方法
- **新检索策略**：实现 `BaseRetriever` 接口，可插拔替换
- **新 LLM 提供商**：在 `LLMClient` 中新增客户端，统一接口
- **新业务系统**：在 `integrations/` 下新增客户端类

## 6. 安全设计

### 6.1 数据安全

- **私有化部署**：所有数据存储在企业内网，数据不出厂
- **SSO 认证**：对接企业统一身份认证，未授权用户无法访问
- **权限控制**：基于角色的访问控制（RBAC），不同部门只能访问本部门文档
- **审计日志**：所有查询和操作记录可追溯

### 6.2 模型安全

- **输入过滤**：防止 Prompt Injection，对用户输入做安全过滤
- **输出校验**：防止模型生成有害内容，输出内容安全检查
- **敏感信息脱敏**：日志和缓存中对敏感信息（身份证、手机号）脱敏
